# RockSnakePlayableTest — первая задача для dots / Jarvis

Версия ТЗ: 0.1 · 13 октября 2026 года.

## 1. Результат задачи

Собери настоящий играбельный браузерный прототип по приложенному видеореференсу. Запусти его на своей VM и открой в браузере этой VM, чтобы Илья мог лично поиграть. Нужна работающая игра, а не только код, скриншоты, запись видео или автоматически проигрываемая демонстрация.

В первой версии вся графика создаётся программно из примитивов Three.js. Не жди моделей, не запускай Blender и генераторы ассетов, не покупай инструменты. Главное — повторить основной игровой цикл и удобное управление мышью и пальцем.

Целевой приватный репозиторий:

https://github.com/IliaMerkurev/RockSnakePlayableTest

Владелец: `IliaMerkurev`. Первая рабочая ветка: `prototype/0.1`.

**Статус на момент подготовки этого пакета: репозиторий из чата не создан, его существование не подтверждено. Указанный URL — точный целевой адрес, а не подтверждение создания.** Проверь его доступность. При наличии авторизованного GitHub CLI на своей VM создай приватный репозиторий, если он ещё не существует. Не называй создание завершённым без успешного ответа GitHub и проверки `isPrivate: true`.

## 2. Обязательное правило Git

**В `main` ничего не пушить и ничего не мерджить, пока Илья отдельно и прямо не скажет это сделать.** Успешные тесты, готовый прототип, завершение задачи или открытый pull request не являются разрешением на merge.

Вся разработка — в отдельных ветках: сначала `prototype/0.1`, далее при необходимости `feature/<название>` и `fix/<название>`. В ветку прототипа можно делать несколько небольших осмысленных коммитов и пушить их по мере работы. Не использовать force-push, `push --all`, `push --mirror`, автоматический merge, изменение видимости репозитория или обход защиты веток.

Если `main` уже существует, создай рабочую ветку от неё и по готовности открой **draft pull request**, но не мерджи и не включай auto-merge. Если репозиторий пустой и `main` отсутствует, первым пушем отправь только `prototype/0.1`. Не создавай и не наполняй `main` самостоятельно ради возможности открыть PR. Отсутствие PR в таком случае объясни в отчёте.

Перед первым пушем проверь владельца, адрес `origin`, приватность и текущую ветку. Подключи локальный защитный хук из пакета: `git config core.hooksPath .githooks`. Это дополнительная локальная защита, не замена серверным правилам GitHub.

Пример подготовки для **уже существующего** репозитория:

Если репозитория действительно нет и есть соответствующая авторизация:

Не добавляй `--add-readme`, `--public` или автоматическую инициализацию `main`. Если имя занято, доступ неоднозначен либо GitHub отклоняет создание, не создавай другой репозиторий и не меняй видимость. Сообщи точную ошибку; продолжай локальную реализацию, если это возможно, не утверждая, что изменения уже на GitHub.

После добавления и проверки файлов пушить **только текущую рабочую ветку**:

```bash

# Выполнять из prototype/0.1:
```

Не класть в git секреты, node_modules, тяжёлый исходный видеореференс и локальные временные файлы. План, исходники, lockfile, небольшие отчёты и тесты должны быть в рабочей ветке.

## 3. Референс и утверждённые изменения

Видеореференс: `zm_vd_1637_0323_v1_FR_1080x1920_59s_EN.mp4`, длительность около 59 секунд. Кадры для ориентира приложены в `docs/reference-contact.jpg`. Видео нужно использовать как референс механик и компоновки, не переносить из него логотип, название Zombie Miner, чужие модели или готовую графику.

В референсе основной цикл: бочки на нижнем конвейере → открытие и получение работников/бонусов → перетаскивание работников на площадки → автоматическая добыча движущейся цепочки ресурсов → монеты → открытие дополнительных площадок. Два работника одинакового уровня объединяются в следующего, в том числе при переносе к уже работающему. Есть бонусные монеты и бомба для разрушения участка цепочки.

Утверждённые пользователем изменения:

* Персонажи не зомби. Пока это нейтральные человечки из примитивов; окончательный вид будет выбран позже.
* Одна и та же геометрия персонажа на всех уровнях. Из внешности меняется **только цвет каски**; номер уровня отображается отдельно. Не менять тело, костюм, масштаб и инструмент в зависимости от уровня.
* Вместо деформируемой змеи — последовательность отдельных округлых low-poly камней. Камни остаются жёсткими мешами.
* Вместо гор — простые стены из боксов с простой текстурой кладки. На этом этапе текстуру создать кодом либо использовать плоский цвет до её готовности.
* Вся остальная графика — примитивы, простые материалы и минимум деталей.

Сохранить плотный цветной поток ресурсов, извилистую трассу, нижний конвейер и хорошо различимые места работников. Не заменять игровой цикл абстрактными кнопками «+деньги»/«повысить уровень».

Точные формулы экономики и условия проигрыша из видео не подтверждены. Приведённые ниже числа и правила завершения — стартовые решения для прототипа, а не якобы восстановленные параметры оригинала. Все такие решения отмечать в `docs/DECISIONS.md`.

## 4. Стек

| Слой | Использовать |
|---|---|
| Язык | TypeScript, строгая проверка типов |
| Рендер | Three.js, `WebGLRenderer`, WebGL 2 |
| Разработка/сборка | Vite, Node.js, npm |
| Интерфейс | Обычные HTML/CSS и DOM, без UI-фреймворка |
| Ввод | Pointer Events, единая логика для мыши и touch |
| Анимация примитивов | Собственные короткие tween/easing-функции и вращения групп |
| Эффекты | Небольшой собственный пул частиц/осколков |
| Звук | Необязательные простые Web Audio-звуки; не блокируют сдачу механик |
| Тесты логики | Vitest, только development dependency |
| Браузерные тесты | Playwright, только development dependency |
| Контроль версий | Git/GitHub, приватный репозиторий, рабочие ветки |

Использовать совместимую поддерживаемую LTS-версию Node и стабильные версии зависимостей. В начале работы зафиксировать точную версию Node в `.nvmrc` и версии пакетов в `package-lock.json`. Проверить `engines` выбранных версий. Не обновлять стек в середине задачи без необходимости.

Не использовать Unity, Unreal, PlayCanvas, React, React Three Fiber, Phaser, физический движок, WebGPU, тяжёлую ECS, платный редактор частиц или готовый игровой конструктор. Не подключать GLTF/Draco/KTX2-загрузчики до появления реальной необходимости в следующих версиях.

Node/Vite нужны для разработки и сборки, не как сервер игровой логики. Готовая игра работает на клиенте. В экспорт не должны попадать инструменты тестирования, дев-панели и сервер разработки.

Важно: современный `WebGLRenderer` Three.js требует WebGL 2. Не обещать совместимость со всеми старыми рекламными WebView. При отсутствии WebGL 2 показывать понятное сообщение вместо чёрного экрана. Минимальные версии целевых мобильных WebView согласуем перед рекламной интеграцией.

## 5. Сцена и примитивы

Создать фиксированную перспективную камеру сверху под углом, с умеренной перспективой и читаемостью как в референсе. Орбитальное управление камерой в игре не нужно. Позиция, FOV, дистанция и границы кадра вынесены в конфиг.

Основная композиция — вертикальная, ориентир 9:16. Одна сцена: пол, 4–5 проходов извилистой трассы, низкие разделительные стены, площадки работников и нижний конвейер. Это стартовая компоновка, а не требование точного числа проходов. Стены не закрывают камни и персонажей.

| Объект | Конструкция плейсхолдера |
|---|---|
| Пол, стены, площадки, конвейер | `BoxGeometry`, при необходимости `PlaneGeometry` |
| Камни | `IcosahedronGeometry` с малой детализацией либо `DodecahedronGeometry` |
| Работник | Голова из низкодетальной сферы; тело/руки/ноги из боксов или цилиндров |
| Каска | Отдельная полусфера/низкий цилиндр и простой козырёк |
| Кирка | Два вытянутых бокса, отдельная группа с pivot для удара |
| Бочка и крышка | Низкодетальные цилиндры, простые обручи только при необходимости |
| Монета | Плоский низкодетальный цилиндр |
| Бомба | Низкодетальная сфера и короткий фитиль |

Простую повторяемую кладку сгенерировать один раз на canvas 128×128 или 256×256 и использовать через `CanvasTexture`. Не делать отдельный меш для каждого кирпича. Не загружать изображения из сети. Камни и одежда могут вообще обходиться цветом материала.

Использовать простое освещение: один направленный и один заполняющий/hemisphere light, простые Lambert/Basic-материалы по назначению. Без PBR-наборов, environment maps, bloom, SSAO и динамических теней от всех объектов. При необходимости — простые пятна теней.

Повторяющиеся камни и части декора по возможности рисовать `InstancedMesh`. Геометрия и материалы переиспользуются. Если работники собраны из множества частей, объединить их неподвижные части или использовать инстансинг там, где это оправдано: низкий polycount сам по себе не устраняет лишние draw calls.

## 6. Игровая логика v0.1

### 6.1. Поток камней

Пример стартовых настроек: 120–180 видимых камней, жёсткий лимит 200; 2–3 геометрических варианта и 3 типа ресурса с разными цветом/HP/наградой. Значения корректировать по читаемости и темпу.

Путь задаётся точками либо математической кривой. Кривую разрешено использовать **только для вычисления позиции и направления**. Не создавать деформируемые секции, TubeGeometry или связанную геометрию змеи. Камень перемещается и поворачивается целиком.

Движение задаётся пройденной длиной пути, а не скоростью изменения сырого параметра кривой. Дистанции между камнями должны оставаться понятными и достаточно равномерными. Камни не должны ускоряться на изгибах из-за неравномерной параметризации.

У каждого камня есть стабильный ID, ресурс, HP, награда и координата вдоль пути. После уничтожения появляется читаемый разрыв; мгновенно телепортировать следующий камень в ту же позицию нельзя. Новые камни появляются у входа, дошедшие до выхода удаляются без награды. Для v0.1 поток пополняется, чтобы не закончиться до тестирования всех механик.

Не добавлять самостоятельно здоровье базы, «смерть змеи», обязательную лаву, поражение по таймеру или tower-defense-правила. Видеореференс не даёт надёжного подтверждения этих условий. Декоративный выход потока допустим.

### 6.2. Рабочие площадки и добыча

Сначала открыта одна площадка и на ней стоит один работник первого уровня. Ещё 2–3 площадки видны закрытыми, с ценой и понятным состоянием доступности.

Работник на площадке автоматически выбирает живой камень в радиусе добычи и бьёт его киркой. Работник на ленте и перетаскиваемый работник не добывают. Удар должен иметь фазу попадания, в которой одновременно происходят реакция камня, урон и эффект.

Для v0.1 сначала достаточно повышать урон с уровнем; скорость ударов остаётся отдельным параметром конфига. Повышение уровня должно ощутимо ускорять добычу. Не связывать характеристики с материалом или цветом каски.

За уничтожение камня монеты начисляются ровно один раз, независимо от количества работников и одновременной бомбы. Вылетающие монеты — визуализация уже совершённой операции, а не отдельный источник денег при клике.

### 6.3. Конвейер и бочки

Нижний конвейер действительно движется и регулярно приносит бочки. Это не неподвижная строка кнопок. На старте ориентироваться на 6–8 видимых мест/носителей.

Клик/тап по закрытой бочке открывает её. Возможное содержимое: работник первого уровня, монеты или бомба. Работник и бомба появляются на месте бочки и доступны для перетаскивания. Монеты начисляются автоматически один раз с визуальной реакцией.

Первые несколько бочек и наград сделать детерминированными: гарантировать знакомство с открытием, установкой работника, merge, покупкой места и бомбой. После этого можно использовать seeded RNG с разумными весами. Не оставлять возможность надолго заблокировать обучение неудачной случайностью.

У сущностей и мест есть стабильные ID. Во время перетаскивания резервировать источник и приостанавливать конвейер, чтобы возвращаемый предмет не оказался в занятом или уехавшем месте. Неподобранные работники и бомбы у конца ленты не должны незаметно исчезать: при заполнении лента/спавн приостанавливаются и возобновляются после освобождения места.

Не делать покупку обязательной для появления первых работников: в стартовой экономике с нулём монет пользователь должен иметь возможность начать игру без отладочных кнопок.

### 6.4. Перенос и объединение работников

Перетащить работника на свободную открытую площадку — поставить его работать. Перетащить обратно на свободное место ленты — вернуть в резерв. Разрешить перенос между площадками.

Перетаскивание на работника того же уровня объединяет их: `L + L → L+1`. Механика работает на ленте и на площадках, в том числе при переносе к уже работающему персонажу. В целевой позиции остаётся один работник следующего уровня, источник освобождается. Цвет каски и номер уровня меняются; геометрия тела остаётся прежней.

Для первой версии задать конфигурируемый максимум, например 5 уровней. Попытка объединить двух работников максимального уровня отклоняется без потери объектов. Разные уровни не объединяются. Swap разных уровней пока не делать: невалидный перенос возвращается на источник.

Изменение GameState выполняется одной атомарной операцией. В любой момент один работник принадлежит только одному месту либо активному drag. Повторный `pointerup`, быстрое двойное нажатие и несколько пальцев не должны дублировать персонажей.

### 6.5. Экономика и открытие площадок

Цены, стартовые деньги, награды, HP, урон, частота ударов, скорость потока и интервал бочек находятся в одном конфиге. Стартовые ориентиры цен дополнительных площадок — 50/150/300 монет; это значения для настройки, не измеренные данные оригинала.

Цена явно отображается. Недостаточно денег — покупка не происходит, баланс не становится отрицательным. Повторный тап не списывает стоимость повторно. После покупки площадка становится доступной для установки работника.

Баланс подобрать так, чтобы без читов первое объединение и первая покупка были доступны в первые десятки секунд. Не требовать от пользователя минут монотонного ожидания до первого интересного действия.

### 6.6. Бомба

Бомба появляется из соответствующей бочки и перетаскивается на трассу. Во время drag показывать круг области действия и валидность цели. При корректном сбросе уничтожить живые камни в показанной области, начислить награду один раз и удалить бомбу.

При сбросе вне трассы либо отсутствии валидной цели вернуть бомбу на источник. Без физического движка, сложного разрушения и реальной симуляции взрыва: короткая вспышка, несколько осколков, реакция объектов.

### 6.7. Обучение, цель и перезапуск

Ненавязчивые подсказки: открыть бочку → поставить работника → объединить одинаковых → открыть новое место → использовать бомбу. Подсветка должна реагировать на реальное состояние. Не блокировать все остальные действия ради жёстко записанного сценария.

Для тестовой демонстрации можно считать промежуточной целью работника третьего уровня и покупку дополнительной площадки. После достижения показать небольшое сообщение с возможностью продолжить либо перезапустить. Это не рекламное обязательство и не окончательный баланс. Ориентир длительности демонстрационного цикла — 45–90 секунд; в режиме теста не обрывать игру принудительно по таймеру.

Кнопка Restart полностью сбрасывает игру, резервирование мест, эффекты, таймеры, drag и обучение. Рестарт не требует перезагрузки страницы. Сохранения между запусками сейчас не нужны.

## 7. Ввод: одинаково полноценные мышь и touch

Использовать единый `PointerController`: `pointerdown`, `pointermove`, `pointerup`, `pointercancel`, `lostpointercapture`. Pointer capture удерживает активный drag при выходе указателя за исходный объект. Не делать независимые конкурирующие mouse/touch обработчики с двойным срабатыванием.

Хранить один `activePointerId`. Дополнительные пальцы не начинают второй drag и не сбрасывают первый. Мышь активирует игровые действия левой кнопкой. Правый клик, выход указателя, потеря фокуса и отмена системного жеста не должны оставлять предмет «приклеенным» к курсору.

Тап отличать от drag порогом перемещения в CSS-пикселях — стартово 8–12 px, параметр в конфиге. Открывать бочку один раз после завершённого тапа, а не одновременно на `pointerdown` и синтетическом `click`. Для обычных DOM-кнопок использовать одну согласованную схему активации и не дублировать игровую команду.

На интерактивной области установить `touch-action: none`; исключить выделение текста и прокрутку страницы при управлении игрой. Не полагаться на hover, колесо мыши, клавиатуру или правую кнопку для обязательных действий.

Расчёт луча и экранных координат вести относительно **реального bounding rect canvas**, с учётом полей вокруг вертикальной игры и текущего размера, а не относительно всего окна. Перемещать drag-view по игровой плоскости и выбирать валидную цель через явные hit-зоны.

Зоны тапа проектировать не меньше примерно 44–48 CSS px в контрольных мобильных разрешениях; это наше UX-требование. Для маленьких мешей разрешены более крупные невидимые области выбора. При touch сместить визуал перетаскиваемого объекта немного выше пальца, но не смещать логическую точку сброса без понятной индикации.

До отпускания подсвечивать площадку, возможный merge либо область бомбы. При невалидном сбросе возвращать объект. Отмена pointer, скрытие вкладки или изменение ориентации во время drag должны безопасно отменять операцию и освобождать все резервации.

## 8. Адаптация экрана и VM

Проверить минимум 360×640, 390×844, 768×1024 и 1280×720 CSS px. Основная вертикальная композиция не должна превращаться в растянутую сцену на десктопе. Можно ограничить ширину игрового viewport и оставить аккуратные поля; лучи выбора учитывают эти поля.

Горизонтальный режим обязан оставаться играбельным, а не только показывать просьбу повернуть телефон. Для него разрешена отдельная настройка камеры/раскладки HUD. Сохранить читаемость целей и размеры hit-зон. Учесть safe-area отступы и не закрывать кнопками важные участки игрового поля.

Поднять сервер на VM. Для браузера внутри VM достаточно loopback-адреса. В отчёте указать фактический URL, например `http://127.0.0.1:5173`, но только после проверки, что сервер там действительно работает. Проверить также production HTML на отдельном preview-сервере.

Если среда поддерживает безопасный проброс портов/встроенный preview, дать пользователю фактически проверенную ссылку. Не называть `localhost` на VM ссылкой, доступной с телефона пользователя. Для внешнего preview использовать только возможности среды и точную разрешённую конфигурацию хоста; не публиковать приватный код или проект через публичный хостинг без отдельного указания.

Процесс сервера должен оставаться запущенным на время передачи результата. Открыть вкладку с игрой и проверить управление вручную. Не завершать задачу словами «можно запустить», когда сервер не запущен.

## 9. Архитектура без лишней сложности

Разделить состояние игры, команды/симуляцию, рендер, ввод, HUD и интеграцию с контейнером рекламы. Не строить универсальный игровой движок. Предлагаемая структура — ориентир, допускаются небольшие упрощения:

```text
src/
  main.ts
  game/
    config.ts
    GameState.ts
    Simulation.ts
    commands.ts
  systems/
    StoneFlow.ts
    Conveyor.ts
    Mining.ts
    Merge.ts
    Economy.ts
  render/
    SceneFactory.ts
    PrimitiveFactory.ts
    EntityViews.ts
    Layout.ts
  input/
    PointerController.ts
  ui/
    Hud.ts
  platform/
    PlayableBridge.ts
scripts/
  build-single.mjs
  check-budget.mjs
tests/
  unit/
  e2e/
docs/
  DECISIONS.md
  TEST_REPORT.md
```

GameState хранит ID, уровни, ресурсы, деньги и занятость мест, но не использует меши как единственный источник истины. Команды проверяют предусловия до изменения состояния. Тесты merge/покупки/наград не требуют WebGL.

Для будущей замены персонажа выделить небольшой контракт визуала: создание, позиция/направление, `setLevel`, `setAction`, уничтожение. У плейсхолдера каска и группа руки/инструмента доступны отдельно. Ось Y — вверх; персонаж имеет pivot у ног. Не загружать будущую GLB-модель и не проектировать сложный скелетный пайплайн сейчас.

Симуляция не зависит от FPS: fixed timestep либо аккуратно ограниченный delta time, один управляемый цикл. При `visibilitychange` ставить симуляцию и звук на паузу, отменять drag. После возврата не проигрывать накопленные минуты добычи и не телепортировать поток вперёд. При перезапуске не плодить новые циклы, подписки и таймеры.

Эффекты ограничены по количеству и переиспользуются. Не создавать тысячи объектов каждый кадр. Освобождать GPU-ресурсы корректно, учитывая, что геометрия и материалы могут быть общими для многих экземпляров.

## 10. Ограничения playable: требования и наши ориентиры

Пока рекламная сеть не выбрана. v0.1 — браузерный прототип с проверяемым автономным экспортом, **не сертифицированный рекламный креатив**. Проверенные ориентиры форматов приведены в официальных источниках в конце документа.

Unity Ads: один минифицированный HTML со встроенными ресурсами, размер меньше 5 МБ, MRAID 3.0; поддержка двух ориентаций, корректная видимость контейнера и переход в магазин только по действию пользователя. Google App campaigns: ZIP до 5 МБ, до 512 файлов, адаптивность и отдельные правила интеграции выхода. Это разные форматы и контракты, а не один универсальный SDK.

Для проекта принять следующие правила:

| Параметр | Требование v0.1 |
|---|---|
| Экспорт | `dist/playable/index.html`, автономный после загрузки документа |
| Внешние загрузки в браузерном экспорте | Нет CDN, remote textures/fonts/models, API, аналитики и иных запросов |
| Размер примитивного прототипа | Желательная цель ≤ 2 000 000 байт; превышение отразить и объяснить |
| Жёсткий проектный предел | `< 5 000 000` байт итогового HTML; равенство лимиту уже ошибка |
| Цель с будущими моделями | Около 4 000 000 байт или меньше, с резервом до лимита |
| Геометрия | Ориентир ≤ 50 тыс. видимых треугольников; стресс-сцена до ~80 тыс. |
| Draw calls | Ориентир ≤ 80 в обычной сцене, до ~120 в кратком пике |
| Частота кадров | Цель 60 FPS на подходящем устройстве; проверка 30 FPS на выбранном слабом телефоне позже |
| Разрешение рендера | Ограничение devicePixelRatio, стартово до 1.5–2; параметр качества |
| Сохранения/сеть | Состояние только в памяти, без backend и обязательного localStorage |
| Звук | Не запускать до пользовательского жеста; возможность отключить |

Числа производительности — внутренние ориентиры, не нормативы всех рекламных сетей. FPS VM с программным GPU нельзя выдавать за измерение на телефоне. В отчёте указывать фактические условия теста и отличать цель от результата.

Размер измерять по реальному файлу HTML в байтах, не по исходникам, node_modules или gzip-оценке. Включать вес встроенного JavaScript, CSS и ресурсов. Не забывать о накладных расходах кодирования будущих бинарных ресурсов.

Экспорт должен встраивать JS и CSS, не оставлять импортов в соседние файлы, dynamic chunks, HMR, debug-панелей, source maps или ссылок на исходный MP4. На стадии сборки библиотеки можно получать через npm; запрет запросов относится к запуску готовой игры, а не к установке инструментов.

Создать небольшой `PlayableBridge` с браузерной реализацией: ready/start, pause/resume, end, CTA. Сейчас CTA в тесте показывает локальное уведомление; не открывает случайный магазин и не делает redirect. Настоящие MRAID/ExitAPI-адаптеры реализуем после выбора сети. Не обращаться к `window.mraid` без проверки наличия и не выдавать заглушку за рекламную интеграцию.

## 11. Порядок реализации

### Этап A. Подготовка и первый видимый кадр

Проверить/создать приватный репозиторий, подготовить `prototype/0.1`, скопировать ТЗ и AGENTS.md. Поднять Vite+TypeScript+Three.js. Собрать пол, стены, маршрут и примитивного персонажа. Сразу открыть сцену в браузере VM. Настроить viewport и базовый PointerController.

### Этап B. Первый настоящий игровой цикл

Добавить поток камней, одну рабочую площадку, работника, удары, HP и начисление монет. Затем конвейер, открытие бочек и перенос на площадку. Проверить взаимодействия мышью и touch уже на этом этапе, не откладывать их до финала.

### Этап C. Объединение и прогрессия

Добавить merge на ленте и на площадках, обновление каски/номера, новые площадки и покупку, валидный возврат объектов и защиту от двойных действий. Добавить бочку с монетами и бомбу.

### Этап D. Завершённый прототип

Добавить HUD, короткое обучение, визуальные реакции ударов/merge/денег, Restart, безопасные паузы и адаптацию двух ориентаций. Подобрать стартовый баланс. Не уходить в художественную полировку и генерацию ассетов.

### Этап E. Экспорт, проверка и передача

Получить один автономный HTML, прогнать проверки размера и отсутствия внешних запросов. Выполнить unit/E2E-тесты и ручной проход. Запустить dev и production preview на VM, открыть игру, записать фактические URL. Закоммитить и запушить рабочую ветку, при наличии базы main открыть draft PR. Передать отчёт и **остановиться до обратной связи, не мерджить в main**.

Реализация должна быть последовательной: на каждом этапе сохранять рабочий срез. Если возникает настоящий блокер, точно указать его; не заменять отсутствующую механику декоративной анимацией и не сообщать о несуществующих тестах.

## 12. Проверки и критерии приёмки

Подробная матрица находится в `docs/ACCEPTANCE_CHECKLIST.md`. Обязательный минимум:

1. Без отладочных читов можно открыть бочки, поставить работников, объединить их, заработать монеты, купить площадку и применить бомбу.
2. Все обязательные действия выполняются мышью и touch, включая настоящий drag; одно только уменьшение viewport не считается проверкой сенсорного ввода.
3. Невалидный сброс, отмена pointer, resize, уход вкладки в фон, второй палец и быстрые повторные нажатия не ломают состояние.
4. Merge не дублирует и не теряет работников; разные и максимальные уровни обрабатываются корректно; покупка и уничтожение камня не дают повторных списаний/наград.
5. Перезапуск возвращает начальное состояние; несколько перезапусков не умножают скорость добычи или количество обработчиков.
6. Автономный HTML работает при блокировке всех запросов после загрузки самого документа. В production нет запросов к соседним JS/CSS/моделям, CDN и исходному видео.
7. Пройдены typecheck, unit tests, browser smoke/E2E и проверка веса; нет ошибок приложения в консоли.
8. Пользователь получил запущенную игру на VM, исходники в рабочей ветке либо честный отчёт о блокере push, и фактические результаты проверок.

В тестах логики покрыть merge, проверки занятости, покупку, единичное начисление награды при одновременном уроне, отмену переноса и максимальный уровень. В Playwright проверить desktop mouse и touch-контекст; для drag использовать последовательности touch-ввода, а не только `page.mouse` на мобильном viewport. Эмуляцию не выдавать за тест на физическом iPhone/Android.

Предусмотреть диагностический режим только для разработки: FPS, calls, triangles, число активных камней/эффектов и текущие игровые параметры. В обычном тесте он выключен, в рекламном экспорте чит-команды отсутствуют.

Ожидаемые команды проекта после реализации:

```bash
npm ci
npm run dev
npm run typecheck
npm run test
npm run test:e2e
npm run build:playable
npm run check:budget
npm run preview:playable
```

Названия npm scripts должны соответствовать реальным работающим командам, а не существовать только в README.

## 13. Формат итогового отчёта dots

Укажи название и краткое состояние версии; адрес репозитория и подтверждение приватности; рабочую ветку и SHA запушенного коммита; draft PR, если он существует; фактический URL браузера VM и доступного preview; команды запуска; размер HTML в байтах; какие тесты реально выполнены и их результаты; фактический браузер/GPU-режим теста; известные ограничения.

Добавь несколько скриншотов вертикального и горизонтального режима. Небольшая запись игрового цикла полезна, но не заменяет живую игру. Обнови `README.md`, `docs/DECISIONS.md` и `docs/TEST_REPORT.md`.

Не утверждай, что тесты на настоящих телефонах выполнены, если использовалась только VM. Не называй проект готовым к рекламной сети до отдельной интеграции и проверки. Не сообщай об успешном push без проверки удалённого SHA.

**Задача завершается сдачей v0.1 на примитивах. Генерация моделей, арт-проход, новые механики и merge в main — только после дальнейших указаний Ильи.**

## 14. После проверки пользователем — не выполнять сейчас
